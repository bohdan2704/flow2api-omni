# Перевірка безпеки Flow2API — 26 вересня 2026

Перевірений commit: `6633ad9` (локальний checkout). До перевірки робоче дерево було чистим.

**Висновок: явного бекдора чи прихованого надсилання Google-токенів автору в перевірених шляхах коду не знайдено. Однак запускати цю конфігурацію у відкритому інтернеті й одразу підключати цінні акаунти небезпечно.** Є підтверджені небезпечні налаштування, SSRF та недоліки захисту секретів. Перевірка вихідного коду не підтверджує безпеку готових образів автора, завантажуваних залежностей або зовнішнього браузерного розширення.

## Межі перевірки

Переглянуто автентифікацію й API, мережеві клієнти, зберігання токенів і файлів, логування, CAPTCHA, оновлення Google-сесій, керування браузерами та профілями, адміністративний frontend, Docker/Compose, systemd, скрипти запуску й GitHub Actions. Проведено пошук зовнішніх адрес, запуску команд, динамічного виконання коду та привілейованих налаштувань.

Застосунок, Chrome і сторонні образи не запускалися; залежності не встановлювалися; акаунти не підключалися. Окремі вже прочитані функції виконано через AST із підставними мережевими та DB-залежностями. Це перевірка поведінки функцій, а не повний HTTP penetration test. У середовищі немає pytest, FastAPI, curl-cffi та інших залежностей проєкту, тому наявний тестовий набір не запускався. Поточні CVE всіх прямих і транзитивних залежностей окремим онлайн-сканером не перевірялися.

## Проблеми, які потрібно закрити

### 1. P1 — стандартні секрети дозволяють забрати акаунтні токени

`config/setting.toml:2` містить API-ключ `han1234` і логін/пароль `admin/admin`; ті самі значення є в прикладі та DB defaults (`src/core/schema_defaults.py:21`). `server.host` — `0.0.0.0`, фактичний порт — `18282`.

`src/shared/auth/auth.py:24` порівнює пароль із конфігурацією; `src/api/admin.py:575` створює адміністративну сесію. Отримавши її, можна взяти список акаунтів та викликати `POST /api/tokens/{id}/export`, який повертає повні ST/AT (`src/api/admin.py:682`). Експорт правильно вимагає admin auth; проблема — відомий пароль на старті.

У логіні немає обмеження спроб. Сесії зберігаються в наборі без TTL (`src/api/admin.py:58`, `:408`), діють до logout, зміни пароля або перезапуску відповідного процесу. Сам застосунок не забезпечує HTTPS. Досяжність з інтернету залежить від firewall, reverse proxy та способу запуску; її тут не вимірювали.

**Дія:** випадкові сильні пароль та API-ключ до першого запуску; відмова запускатися зі стандартними значеннями; HTTPS, обмеження доступу до `/api/admin/*` та решти admin endpoints, rate limit і TTL сесій. Після створення БД зміна лише TOML може не змінити активний пароль: старт завантажує конфігурацію з БД (`src/main.py:54`).

### 2. P1 — звичайний Compose запускає чужий образ, незалежно від форку

`docker-compose.yml:5` використовує `ghcr.io/thesmallhancat/flow2api:latest`; `docker-compose.proxy.yml:5` — `thesmallhancat/flow2api:latest`. Форк не змінює ці адреси. Перевірений checkout і вміст такого образу можуть відрізнятися. Тег `latest` змінний: новий pull може завантажити інший код; саме по собі це не означає автоматичного оновлення вже запущеного контейнера.

**Дія:** збирати власний образ із перевіреного commit; за використання registry прив'язувати перевірений образ до digest. `docker-compose.local.yml` і headed-варіант уже мають локальну збірку, але потребують решти змін безпеки. Узгодити порт програми з mapping: поточний TOML задає `18282`, Compose очікує `8000` у контейнері.

### 3. P1 — сторонній JavaScript має доступ до входу й адміністративної сесії

`static/login.html:7` та `static/manage.html:7` підключають `https://cdn.tailwindcss.com` без SRI. Код цього скрипта виконується з правами сторінки: може прочитати введений пароль, `localStorage.adminToken` та викликати API експорту токенів. Збереження admin token у localStorage — `static/login.html:48`.

Це **ризик компрометації постачальника скрипта**, а не доказ того, що Tailwind зараз викрадає дані. Компрометація Google акаунтів можлива через можливість викликати admin export від імені адміністратора.

**Дія:** локально зібраний статичний CSS без runtime CDN-скриптів; CSP; переглянути зберігання сесії (HttpOnly cookie потребуватиме також належного CSRF-захисту).

### 4. P1 — SSRF через URL зображення

`src/api/routes.py:132` / `:180` приймають довільні HTTP(S) URL, не перевіряють IP/мережу після DNS resolution і не обмежують перенаправлення на приватні адреси. `_extract_prompt_and_images_from_openai_messages` передає клієнтський `image_url` у цей завантажувач (`:219`). Достатньо звичайного API-ключа; admin auth не потрібен.

Функція передає localhost, приватні IP та link-local metadata-адреси HTTP-клієнту. Будь-яке непорожнє тіло з HTTP 200 приймає як зображення, без перевірки формату. Це дає запити від імені сервера до внутрішніх сервісів. Отримані байти можуть далі потрапити в upload до Google; пряме повернення довільного внутрішнього файла нападнику або повний takeover сервера цим аудитом не доведено.

**Дія:** allowlist джерел або обов'язкова перевірка схеми й усіх resolved IP, блокування loopback/private/link-local/reserved адрес та перевірка кожного redirect; захист від DNS rebinding, мережевий egress-фільтр, ліміти розміру/часу та валідація зображень. Виправлення traversal у попередньому commit обмежує локальне читання basename, але не усуває SSRF.

### 5. P1 за публікації образу — секрети можуть увійти до Docker build context

Обидва Dockerfile виконують `COPY . .`. `.dockerignore:47` виключає частину DB/log-файлів, але **не** `config/setting.toml`, `logs.txt*`, довільні browser profile-каталоги в репозиторії або весь `data/`. `.gitignore` не є правилом виключення для Docker.

Після локального використання збірка може включити налаштовані секрети, журнали чи профіль, якщо він розміщений усередині build context; публікація такого образу розкриє їх тим, хто може завантажити образ. Стандартний профіль `/opt/flow2api-profiles/...` поза context через `COPY` не потрапляє. Поточний checkout не містить підключених акаунтів. `config/setting.toml` уже відстежується Git: пізніша наявність його в `.gitignore` не зупиняє commit змін цього файла.

**Дія:** explicit allowlist файлів для образу, виключити runtime data/logs/profiles/config; використовувати окремий приклад конфігурації та runtime secrets. Припинити відстеження робочого TOML перед внесенням секретів. Перевіряти склад образу до публікації.

### 6. P2 — браузер без sandbox і слабка ізоляція запуску

`src/services/browser_captcha_personal.py:1217` та `src/services/keepalive/refresher.py:150` запускають Chrome з `sandbox=False`; передбачено також `--no-sandbox`. Dockerfile не задають `USER`, тому за замовчуванням процеси працюють як root **усередині контейнера**. Для основного сервісу Compose немає `cap_drop`, `no-new-privileges` чи read-only root filesystem.

Це збільшує наслідки вразливості Chromium/залежності. Root у контейнері не дорівнює root на хості: в основному Compose немає Docker socket, `privileged: true` або mount всього хоста, прямого container escape не знайдено. Водночас доступ до змонтованих `data`, `tmp`, конфігурації та акаунтних секретів залишається.

Proxy-варіант додатково запускає сторонній `caomingjun/warp`, дає `NET_ADMIN`, TUN та той самий host `./data` (`docker-compose.proxy.yml:20`): компонент отримує доступ до спільної директорії, де лежить БД Flow2API.

**Дія:** окремий непривілейований користувач, окрема VM/контейнер для браузерів, мінімальні mount/права, актуальний Chromium, увімкнути sandbox де можливо; WARP дати окремий volume, не ділити з БД.

### 7. P2 — вимкнена перевірка TLS для медіафайлів

`src/api/routes.py:166`, `src/shared/storage/file_cache.py:128` та `:343` передають `verify=False`. Мережевий посередник може підмінити завантаження. Це стосується цих медіазапитів; основний Flow auth transport не має такого вимкнення, urllib fallback використовує стандартний SSL context (`src/services/flow/transport.py:48`).

**Дія:** увімкнути перевірку сертифікатів, за потреби налаштувати явний довірений CA; не вирішувати помилки TLS глобальним вимкненням перевірки.

### 8. P2 — чутливі локальні дані та публічні медіапосилання

ST/AT пишуться у SQLite без шифрування (`src/core/repositories/token_repository.py:43`), admin password також зберігається як текст (`src/core/schema_defaults.py:35`). Наявність bcrypt helper у коді не означає його використання для цього пароля. Файл БД і директорія створюються без явного приватного mode; права залежать від umask. Профілі onboarding мають окремий захист `0700`/`0600`.

У поточному TOML увімкнено debug (`config/setting.toml:34`). Логер записує тіла запитів/відповідей і proxy URL; поле proxy не маскується (`src/shared/telemetry/logger.py:232`). Request logs окремо зберігають промпти/дані в БД (`src/services/generation_handler.py:2049`). Маскування неповне: контрольна перевірка з фіктивними рядками показала, що `access_token` маскується, а `rotated_st` та `accessToken` — ні. Наявність фактичного шляху запису саме цих двох полів у поточному auth flow не доведена; це прогалина helper, а не підтверджений витік усіх ST у журнали.

`src/main.py:294` монтує `/tmp` без auth. Той, хто знає URL, може завантажити кешоване медіа без API-ключа. Це не доступ до довільної системної `/tmp`: віддається директорія `tmp` саме репозиторію. Для upscale є прямий запис кешу (`src/services/generation_handler.py:775`), тому `cache.enabled=false` не є гарантією відсутності файлів.

**Дія:** приватні права на DB/logs/profiles й захищені backup; пароль хешувати; вимкнути debug за замовчуванням, мінімізувати request logs, виправити redaction. Для приватних медіа — автентифікація або обмежені за часом підписані URL та очищення файлів. Шифрування даних на диску допомагає проти викрадення файлів/backup, але не від процесу, який уже має доступ до ключів.

### 9. P2 — виконувані залежності завантажуються під час роботи

`src/services/captcha/bootstrap.py:24` запускає `pip install` для nodriver/playwright без версії; після невдачі використовує стороннє дзеркало. Chromium також може завантажуватися з альтернативного mirror (`:81`). Частина requirements має діапазони або нижню межу; hash-lock транзитивних залежностей відсутній.

Таке встановлення легітимно пояснюється bootstrap, але означає, що перевірений Git commit не фіксує весь виконуваний код. Це не ознака того, що самі дзеркала шкідливі.

**Дія:** усі компоненти встановлювати на етапі контрольованої збірки з фіксованими версіями й hashes, відключити runtime install та fallback mirrors, сканувати отриманий dependency lock/образ на відомі вразливості.

## Що реалізовано коректно в перевірених місцях

- Адміністративні endpoint мають перевірку окремої випадкової admin-сесії; API-ключ генерації не заміняє її. Звичайний список акаунтів не повертає ST/AT; явний export має `Cache-Control: no-store`.
- Endpoint браузерного extension перевіряє окремий connection token, а акаунт встановлює з перевіреної Google-сесії. CORS має allowlist, не `*`; фактичний TOML містить конкретний extension origin, який слід переглянути для власного deployment.
- Основні SQL-запити з даними користувача параметризовані; запуск subprocess використовує масиви аргументів. Прямої shell injection або довільного server-side виконання команд з API в перевірених шляхах не знайдено.
- Для onboarding/profile management є перевірки symlink, власності процесів, ідентичності акаунта та приватні права директорій; cleanup не виглядає прихованою командою захоплення сервера.
- Жодного знайденого прихованого Telegram/Discord endpoint автора, reverse shell, встановлення SSH-ключа чи cron-backdoor. Наявний Discord transport працює з налаштовуваним URL.

## Результати контрольного виконання

На фіктивних даних, без імпорту застосунку й без мережі:

1. `AuthManager.verify_admin('admin', 'admin')` з поточним TOML повертає `True`.
2. `AuthManager.verify_api_key('han1234')` повертає `True`.
3. Реальне тіло `admin_login` із підставною БД створює токен і додає його до `active_admin_tokens`.
4. `_load_image_bytes_from_uri` передає HTTP-клієнту `127.0.0.1`, `10.0.0.1` і `169.254.169.254`; для кожного `verify=False`, фіктивне не-графічне тіло HTTP 200 приймається.
5. Log sanitizer маскує `access_token`, але залишає повні фіктивні значення `rotated_st` і `accessToken`.

Тестові адреси не відвідувалися. Вихідний код і конфігурація не змінювалися; додано лише цей звіт.

## Рекомендований порядок перед підключенням акаунтів

1. Збирати власний образ із перевіреного коду, прибрати секрети з build context та відстежуваних файлів.
2. Змінити стандартні секрети, обмежити admin-доступ мережею/VPN і налаштувати HTTPS; звірити порти.
3. Прибрати зовнішній JavaScript з admin UI; додати захист від SSRF, TTL/rate limiting і TLS verification.
4. Ізолювати браузер та процес, обмежити mounts/egress; використовувати лише окремі Google-акаунти для генерації.
5. Захистити DB/backup/logs/media, зафіксувати й просканувати залежності. Після змін виконати інтеграційні security-тести в ізольованому середовищі.

Поточний результат — **«явної навмисної крадіжки не виявлено; production-безпека недостатня»**, а не гарантія відсутності всіх вразливостей.
